## 0.1 M4 deterministic simulation architecture

M4 采用 **Deterministic Data-Oriented ECS** 作为 authoritative simulation
architecture。依赖方向固定为：

```text
Formats / Content Core
        ↓
Simulation descriptors
        ↓
RA2YR.Simulation
        ↓
Presentation Adapter
        ↓
Unity
```

`RA2YR.Simulation` 和其数据模型不得引用 `UnityEngine`、`UnityEditor`、
场景对象或渲染对象。Unity DOTS、Jobs、Burst 只能作为未来可替换的执行或
表现性能后端，不能成为 authoritative semantics 的依赖。Unity frame rate
不是 gameplay clock，`GameObject` ID 不是 Entity identity，
`MonoBehaviour.Update()`、`Rigidbody`、`Collider`、`NavMesh` 和 render state
都不得成为 gameplay truth。

ECS 设计要求 hot/cold data separation、shared immutable type descriptors、
batch systems、spatial indexing、event/dirty-driven work、staggered decision
schedules 和 bounded work。禁止每 tick 不受控分配、全世界逐单位扫描和
无序并行写入；性能判断必须由可复现 benchmark 支持，不能用开发机时间冒充
兼容性证据。

### 单一逻辑权威与确定性提交

M4 的线程模型是 **single logical authority + parallel compute + deterministic
commit**：

```text
Tick N
  ↓
Collect Inputs → Canonicalize → Read Snapshot
  ↓
Parallel Compute Proposals
  ↓
Barrier → Deterministic Commit → State Hash
```

worker 可以执行只读的 path query、target evaluation、threat scoring、visibility
query、AI utility evaluation 和 map preprocessing，但不得直接修改 authoritative
world。所有 proposal 必须经过稳定排序、校验和单一 commit 阶段。

### Unit Tactical Autonomy

Unit Tactical Autonomy 是正式的 Project Enhancement gameplay capability，
不是临时 UnitAI hack，也不是 YR original compatibility claim。未来能力包括
`AutoAcquire`、target prioritization、Attack-Move、AutoKite、CrushAvoidance、
HazardAvoidance、AutoRetreat、CoverSeeking、FocusFire、FormationAssist、
AutoAbility 和 tactical repositioning；每项能力都必须有显式 capability、
evidence 和 policy 边界。

单位必须长期支持一级 `UnitAutonomyMode`：

```text
Manual | Assisted | Automatic
```

`Manual` 不是 debug hack。它关闭可选的 AutoKite、AutoCast、AutoRetreat、
smart focus、autonomous pursuit、cover seeking 和 smart dispersal（除非
明确 command policy 允许 AutoAcquire），但仍保留合法路径、occupancy、明确
attack command 和合法移动等 engine correctness。玩家强制命令通常优先于
tactical autonomy，engine legality 始终最高。

最终 `ResolvedAutonomyProfile` 必须由以下输入显式合成，而不是 `IsSmart=true`：

```text
Base Unit Profile + Veterancy + Faction Doctrine + Technology Unlock
+ Temporary Effects + Player Configuration + Current Command Envelope
```

`AutonomyEnvelope` 至少表达 `MayMove`、`MayAcquire`、`MayChase`、`MayRetreat`、
`MayKite`、`MayCast` 和 `MayEvade`。未来 Unit Behavior panel 只能配置已解锁
能力，不能绕过科技、老兵等级或阵营 capability。

### Computer AI 与未来 Neural Platform

Computer AI 只能通过合法 observation 和 command interface 参与：

```text
Strategic AI → Operational AI → CommandRequest
             → Unit Tactical Autonomy → Simulation
```

AI 不得直接写入 `SimulationWorld`。`AIObservation` 必须与人类可见信息共享
同一 fog/visibility 规则，不得暴露 fog 后单位、敌方资金、生产队列、hidden
units、future state 或 hidden random result。AI 手速由 `CommandBudget`、
`DecisionInterval`、`ReactionDelay` 和 `MaxOperationalCommandsPerWindow`
约束；难度优先改变 policy/planning/decision quality，而不是偷偷加钱或加攻击，
未来作弊必须显式使用 `HandicapProfile`。

未来 backend 分为 `RuleBased`、`Neural`、`Hybrid`；RuleBased 永远保留作为
reference、fallback、MOD 和模型不可用时的 deterministic policy。Neural 只能
替换 policy，不能成为 simulation authority：

```text
Observation → IAgentPolicy → AgentDecision → Validation
            → CommandRequest → Simulation
```

M4 只建立 observation/policy/action 合同、schema version、model descriptor、
headless environment 和 telemetry/replay separation；不下载模型、不安装 ML
framework、不引入 ONNX runtime、不训练网络。训练 telemetry 不是 authoritative
replay state；未知 MOD content 或模型不兼容时必须 fail safely 并回退 RuleBased。

### M4 证据边界

M4 synthetic world、headless battle、benchmark 和 deterministic hashes 证明
项目增强 simulation contract，不证明 YR 1.001 original-runtime equivalence。
原版兼容、FinalAlert 往返、clean baseline、ProjectBaseline terrain binding 和
community extension semantics 仍按兼容矩阵独立记录。所有旧文档中的数字、坐标
和时间规范都必须标记为 `Compatibility Target`、`Configured Profile` 或
`ConfirmedByOriginalRuntime` 之一；没有证据时不得使用最后一种标签。

## 1. 项目定义

本项目旨在使用 Unity 重新实现一套可独立运行的《红色警戒2：尤里的复仇》v1.001 兼容引擎。Unity 负责窗口、平台、输入、音频、资源呈现及编辑器扩展等基础能力；原版游戏的数据格式、配置体系、地图规则、战斗逻辑、AI 行为和视觉表现，由本项目自主编写的 C# 代码解释与执行。

本项目不是“制作一款类似红警2的 RTS”，也不是仅复刻界面、地图或少量单位，而是建立一套能够读取原版数据、解释原版规则、复现原版行为，并可承载社区模组扩展的开源开发底座。

长期目标如下：

1. 在不分发 EA/Westwood 版权素材的前提下，读取用户本地合法持有的游戏内容。
2. 对 YR 1.001 原版素材、配置、地图和行为形成可验证的兼容能力。
3. 对 FinalAlert 2 地图形成可靠的读取、运行与写回能力。
4. 在第一阶段兼容原版后，逐步承载 Ares、Phobos、Kratos、DynamicPatcher 等社区扩展语义。
5. 在保持兼容层稳定的前提下，允许未来增加原版不具备的新功能。

## 2. 法律、版权与仓库边界

### 2.1 开源仓库允许包含

- 自主编写的引擎代码；
- 自主编写的编辑器工具；
- 自主编写的格式说明、测试代码和技术文档；
- 自主生成或明确允许再分发的测试样本；
- 不含原版版权素材的演示内容。

### 2.2 开源仓库不得包含

- 原版 MIX 内容；
- 解包后的原版 SHP、VXL、HVA、TMP、PAL、PCX、WAV、CSF 等文件；
- 原版地图、战役资源、语音、音乐或美术素材；
- 未经许可复制的第三方模组资源；
- 不能确认许可证兼容性的第三方源代码。

### 2.3 本地内容目录

引擎必须支持从仓库外部的本地目录读取用户提供的 YR 1.001 文件。原版文件应被视为外部内容，不应成为 Unity 工程源码的一部分，也不应被自动提交至 Git。

### 2.4 开源参考项目使用原则

可以研究公开文档、公开逆向成果和开源项目的格式定义与行为描述，但必须：

- 遵守对应项目许可证；
- 保留必要的许可证和署名；
- 避免将许可证不兼容代码直接复制进本项目；
- 对关键格式和行为建立本项目自己的测试依据；
- 对尚未确认的字段、算法和原版行为明确标记，不以猜测替代证据。

### 2.5 项目声明

项目文档应明确：

- 本项目不是 EA 官方产品；
- 《Command & Conquer》《Red Alert》《Yuri's Revenge》及相关素材权利归其权利人所有；
- 本项目仅提供兼容引擎代码，不提供原版游戏内容；
- 若权利方提出合法异议，项目维护者将按实际情况处理仓库和传播问题。

## 3. 兼容性基线与判定标准

### 3.1 基线版本

第一阶段的权威兼容基线为：

- 《红色警戒2：尤里的复仇》v1.001；
- 原版 YR 1.001 配置文件和素材；
- FinalAlert 2 可生成和编辑的 YR 地图；
- 原版游戏可观察、可复现的实际行为。

红警2本体、非 1.001 版本、第三方补丁和扩展平台可以作为参考，但不能覆盖 YR 1.001 基线。

### 3.2 兼容状态

每项功能应独立记录以下状态，避免把“能读文件”等同于“完全兼容”：

1. 未识别；
2. 可解析；
3. 可保存；
4. 可呈现；
5. 可执行；
6. 行为近似；
7. 原版对照通过；
8. FinalAlert 2 往返通过；
9. 完全兼容候选；
10. 已确认限制。

### 3.3 “完全兼容”的判定

“完全兼容”不能仅凭主观体验宣布。至少应满足：

- 原版数据可稳定读取；
- 原版单位、建筑、武器、地图、AI 和任务可运行；
- 关键数值、时序、目标选择、路径、伤害、生产和触发结果与原版一致；
- 原版地图读取和写回后，不出现无关内容丢失或结构损坏；
- 兼容矩阵中的原版必需项全部通过；
- 已知差异均有可复现案例、原因说明和状态记录。

# 第一阶段：完整重制 YR 1.001 基础功能

## 4. 第一阶段总体目标

第一阶段要求完成一套可独立运行的 YR 1.001 兼容引擎，使用户在提供本地原版内容后，可以进入游戏前端、选择模式、加载地图、控制单位、建设基地、生产作战、执行任务、与电脑玩家对战，并获得与原版高度一致的素材表现、规则结果和操作体验。

第一阶段不以“最小可玩版本”为最终验收目标。可以存在中间版本，但第一阶段结束时应覆盖原版 YR 1.001 的全部基础系统、原版单位行为和原版地图语义。

## 9. 游戏时间、坐标和确定性

### 9.1 时间规范（Compatibility Target / Configured Profile）

- **1 游戏秒 = 15 个逻辑 Tick** 是当前 YR compatibility target 和显式
  configured profile；本仓库目前不把它单独标记为 `ConfirmedByOriginalRuntime`。
- 逻辑 Tick 与显示帧率分离；
- 暂停、加速、减速、单步和重放均基于逻辑 Tick；
- 动画、武器射速、生产、超武、任务计时和 AI 计时使用同一基准。

### 9.2 坐标规范（Compatibility Target / Configured Profile）

- **1 单元格 = 256 leptons**、**网格高度 = 208 leptons** 和约 24° 等距
  视觉角度均是兼容目标或 configured profile，除非兼容矩阵提供独立原版
  对照，不得写成原版 runtime confirmed truth；
- 地图格、逻辑坐标、显示坐标和高度坐标必须可相互转换；
- 核心逻辑以稳定整数坐标为权威；
- 浮点显示误差不得反向改变逻辑结果。

### 9.3 确定性

同一地图、配置、输入序列和随机种子，应产生一致逻辑结果。至少保证：

- 对象创建顺序稳定；
- 随机数调用顺序可追踪；
- 目标选择稳定；
- 路径结果稳定；
- 伤害结算顺序稳定；
- 同 Tick 事件顺序稳定；
- 存档、回放和联机状态可序列化；
- Unity 渲染帧率变化不改变战斗结果。

- 确定性 Tick；
- 输入同步；
- 延迟处理；
- 暂停与掉线；
- 反不同步诊断；
- 结果统计；
- 版本和内容校验。

无需复刻已关闭的官方在线服务，但应保留可用的局域网或现代替代入口。

---

## 20. 工具、诊断和开发体验

项目应提供：

- 内容目录检查；
- 文件索引；
- 格式查看；
- 十六进制偏移定位；
- SHP、PAL、VXL/HVA、TMP 查看；
- 地图结构查看；
- INI 引用追踪；
- CSF 标签查看；
- 资源缺失和地图非法内容报告；
- Tick 单步；
- 随机数调用追踪；
- 对象状态和路径查看；
- 深度排序查看；
- AI 当前任务查看；
- 触发事件日志；
- 存档差异；
- 回放不同步定位；
- 原版与重置引擎对照结果。

这些工具应帮助开发者回答：哪个源文件、哪个节、哪个键、哪个二进制偏移、哪个对象和哪个 Tick 导致差异。

---

## 21. 第一阶段测试与验收

### 21.1 格式测试

每种格式应具备：

- 正常样本；
- 最小样本；
- 空内容；
- 截断内容；
- 非法长度和非法索引；
- 未知字段；
- 多版本差异；
- 往返测试；
- 模糊测试或等价健壮性测试。

### 21.2 原版黄金样本

原版文件只在本地测试环境使用。应记录：

- 图像尺寸、帧数、帧偏移和调色结果；
- 像素哈希或容差比较；
- VXL 边界和体素数量；
- HVA 矩阵；
- 地图对象数量和 Pack 解码结果；
- INI 强类型值；
- CSF 文本；
- 音频元数据。

仓库 CI 使用自主生成的合成样本。

### 21.3 行为对照

应建立可重复的原版对照场景，覆盖：

- 移动和转向；
- 路径；
- 射速和伤害；
- 目标选择；
- 生产时间和资金变化；
- 电力和视野；
- 超武充能；
- AI 小队；
- 触发；
- 桥梁、驻军、心灵控制和采矿；
- 存档恢复；
- 回放一致性。

### 21.4 地图往返

应验证：

- 原图可被 FinalAlert 2 打开；
- 引擎可读取；
- 引擎写回；
- FinalAlert 2 可再次打开；
- 未修改对象和触发语义不变；
- Pack 数据可重新解析；
- 预览图和地图尺寸一致；
- 差异报告可解释。

---

## 22. 第一阶段完成条件

第一阶段完成不能仅以“能进入一局游戏”判定。至少应满足：

1. 原版内容目录可被可靠识别和加载。
2. 原版主要素材格式可正确显示和播放。
3. YR 1.001 原版 Rules、Art、AI 和相关配置可被解释。
4. 原版地图和 FinalAlert 2 地图可运行。
5. 原版地图具备可靠写回能力。
6. 原版阵营、国家、单位、建筑、武器、超武和特殊机制可运行。
7. 战役、遭遇战、AI、触发、存档和基础多人能力可用。
8. 15 Tick 逻辑、leptons 坐标和确定性得到验证。
9. 关键视觉效果、深度排序和体素表现达到原版兼容目标。
10. 兼容矩阵、已知差异、测试结果和复现步骤完整。
11. 不依赖仓库内的原版版权素材。
12. 不以未经验证的“完全兼容”替代测试证据。

---

# 第二阶段：社区扩展平台兼容

## 23. 第二阶段总体目标

在第一阶段稳定、可测试且不再频繁改变核心语义的基础上，增加对 Ares、Phobos、Kratos、DynamicPatcher 等扩展平台的兼容，使使用其扩展标签和行为的模组能够被识别、解释和运行。

第二阶段不是简单允许未知标签存在，而是实现扩展标签对应的实际运行语义。

---

## 24. 扩展配置兼容

应支持：

- 扩展平台新增类型和注册列表；
- 新增 Rules、Art、AI 和地图标签；
- 新增武器、弹头、抛射体和动画语义；
- 新增单位、建筑和超级武器行为；
- 新增触发事件和动作；
- 新增 UI 和音频引用；
- 平台版本差异；
- 标签别名、弃用和兼容模式。

不同扩展平台可能对同一标签有不同语义，必须按平台和版本区分。

---

## 25. 扩展运行时兼容

应能承载社区扩展常见能力，例如：

- 更复杂的单位状态；
- 自定义护盾、资源和经验；
- 新型武器、抛射体、弹头和超级武器；
- 更复杂的 AttachEffect；
- 脚本或动态补丁；
- 运行时标签修改；
- 新型动画和显示层；
- 扩展 AI 和触发；
- 自定义 UI；
- 模组自定义数据。

应建立可持续更新的扩展兼容矩阵。

---

## 26. 扩展隔离与冲突

应确保：

- 第一阶段原版语义不因扩展层改变；
- 扩展功能按内容包启用；
- 模组声明所需平台和最低版本；
- 多扩展平台同时存在时检测冲突；
- 未支持标签产生明确诊断；
- 不支持行为不能静默忽略；
- 错误可定位到标签、对象和来源文件；
- 存档、回放和多人校验包含扩展平台版本。

---

## 27. 第二阶段完成条件

第二阶段完成以选定版本的扩展兼容矩阵为依据：

- 扩展标签可解析；
- 扩展行为可执行；
- 代表性模组可载入；
- 关键机制有自动测试；
- 不支持项有明确报告；
- 原版兼容测试仍全部通过；
- 多人、存档和回放能识别扩展版本；
- 扩展平台更新时有清晰适配流程。

---

# 第三阶段：自主扩展与现代化能力

## 28. 第三阶段总体目标

第三阶段允许在原版兼容层和社区扩展层之外增加自主功能。新增功能不再受原版技术限制，但必须保持兼容内容仍可按原版规则运行。

---

## 29. 自主扩展方向

可支持但不限于：

- 真 3D 视角；
- 可旋转、缩放相机；
- 现代光照和高分辨率素材；
- 更复杂的物理表现；
- 单位被冲击掀起；
- 更大地图和更多玩家；
- 更高单位数量；
- 现代网络同步、服务器权威、旁观、回滚和重连；
- 录像分享；
- 模组热重载；
- 可视化规则、地图和 AI 编辑器；
- 脚本 API 和插件系统；
- 内容包管理；
- 跨平台和无障碍功能；
- 更现代的 UI 和输入方式。

---

## 30. 兼容模式与增强模式

### 30.1 原版兼容模式

- 使用第一阶段逻辑；
- 保持 15 Tick；
- 保持原版坐标和关键数值；
- 禁用会改变原版结果的增强功能；
- 允许原版对照测试；
- 允许运行原版地图和内容。

### 30.2 社区扩展兼容模式

- 使用第二阶段声明的平台语义；
- 按模组要求启用功能；
- 校验扩展版本；
- 保持对应平台的行为目标。

### 30.3 自主增强模式

- 允许启用新系统；
- 允许改变画面和规则；
- 内容包声明依赖；
- 存档、回放和联机记录增强功能；
- 不把增强模式结果误标为原版兼容结果。

---

## 31. 第三阶段稳定性要求

自主扩展不得破坏：

- 原版格式读取；
- 原版地图和规则；
- 第一阶段自动测试；
- 第二阶段扩展兼容；
- 存档和回放版本识别；
- 多人内容校验；
- 未知标签保留；
- 原版内容目录只读边界。

---

# 共同工程要求

## 32. 代码边界

核心格式、配置和逻辑应尽量保持：

- 可独立测试；
- 不依赖场景对象生命周期；
- 不依赖 Unity 物理作为权威逻辑；
- 不依赖显示帧率；
- 不使用渲染结果反推逻辑状态；
- 可用于命令行测试；
- 可用于地图工具；
- 可用于服务器或无界面模拟；
- 可序列化、可诊断、可版本化。

Unity 集成层负责把核心状态呈现为画面、声音和输入，不应成为规则真相的唯一来源。

---

## 33. 数据完整性

所有解析器和写回器应：

- 检查输入边界；
- 不信任文件长度、索引和字符串；
- 不静默截断；
- 不静默替换未知值；
- 保留来源信息；
- 支持错误定位；
- 对损坏文件给出可理解提示；
- 避免单个损坏素材导致整个项目无法启动；
- 对地图写回提供备份和差异报告。

---

## 34. 文档要求

项目应持续维护：

- 总体需求；
- 架构说明；
- 格式说明；
- 兼容矩阵；
- 已知差异；
- 测试说明；
- 本地内容目录说明；
- 版权边界；
- 第三方许可证；
- 存档、回放和网络协议版本；
- 版本更新记录；
- 重大决策记录。

---

## 35. 最终原则

1. 兼容性优先于“看起来差不多”。
2. 原版行为优先于主观设计偏好。
3. 测试证据优先于口头宣称。
4. 未知内容应保留和报告，不应静默丢弃。
5. 核心逻辑与显示帧率分离。
6. 原版素材始终位于用户本地，不进入开源仓库。
7. 第一阶段稳定后再承载社区扩展。
8. 自主增强功能不得污染原版兼容模式。
9. 无法确认的二进制结构和行为必须请求样本或建立实验，不以猜测完成。
10. “完全兼容”是测试结果，不是项目宣传语。
