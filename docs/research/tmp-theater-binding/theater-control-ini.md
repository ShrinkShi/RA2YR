# Theater control INI

## 1. Responsibility

The theater control INI is not part of the TMP binary format. It describes a theater registry that connects logical TileSets, TMP filename stems, global tile-number ranges, LAT transitions, and special terrain roles.

It must enter the system through the already established content pipeline:

```text
content discovery
→ ordered same-name INI layers
→ lossless INI documents
→ semantic section/key composition
→ typed TheaterControl view
```

The theater loader must not scan the disk or MIX archives itself.

## 2. Theater families

The project should represent at least these RA2/YR profiles independently:

| Logical theater | Common TMP extension | Common ISO-palette stem | Notes |
|---|---|---|---|
| Temperate | `.tem` | `isotem.pal` | shared RA2 base role |
| Snow | `.sno` | `isosno.pal` | snow/ice-specific registry roles |
| Urban | `.urb` | `isourb.pal` | RA2 urban family |
| NewUrban | `.ubn` | profile-specific ISO palette | YR expansion; editor fallback conflicts |
| Desert | `.des` | `isodes.pal` candidate | YR expansion |
| Lunar | `.lun` | `isolun.pal` candidate | YR expansion |

Exact control INI names, palette names, content MIX mounts, and fallback behavior must be data-driven. They must not be generated by one global string-replacement rule.

## 3. Control INI sources

Community documentation identifies control-file families such as:

- `temperat.ini` / `temperatmd.ini`;
- `snow.ini` / `snowmd.ini`;
- `urban.ini` / `urbanmd.ini`;
- `urbannmd.ini` candidate for NewUrban profiles;
- `desertmd.ini`;
- `lunarmd.ini`.

The exact archive location and layered participation are content-discovery concerns. RA2 and YR variants can both contribute to the effective document under the configured project composition policy.

A high-priority theater INI layer must override individual section/key identities while inheriting unspecified lower-layer values. Whole-file winner behavior is not used.

## 4. `[General]` role keys

Public editor/tool implementations recognize keys including:

- `RampBase`;
- `RampSmooth`;
- `SlopeSetPieces`;
- `CliffSet`;
- `WaterSet`;
- `ShorePieces`;
- `BridgeSet`;
- `TrainBridgeSet`;
- `WoodBridgeSet`;
- `Ice1Set`, `Ice2Set`, `Ice3Set`, `IceShoreSet`;
- terrain/LAT pairs such as `RoughTile` / `ClearToRoughLat`;
- `SandTile` / `ClearToSandLat`;
- `PaveTile` / `ClearToPaveLat`;
- `GreenTile` / `ClearToGreenLat`.

These values refer to TileSet registry indices, not directly to global map tile IDs or TMP filenames.

The typed reader must preserve:

- raw key occurrence and provenance;
- resolved effective value;
- parsed integer candidate;
- missing/out-of-range state;
- extension-profile origin.

## 5. `[TileSet####]` sections

The strongest section grammar is four decimal digits:

```text
[TileSet0000]
[TileSet0001]
...
```

Common fields include:

- `SetName`;
- `FileName`;
- `TilesInSet`;
- `Morphable`;
- `MarbleMadness`;
- `NonMarbleMadness`;
- `AllowTiberium`;
- editor/extension keys.

A lossless reader retains every section, including:

- duplicate section occurrences;
- malformed suffixes;
- missing numbers;
- numbers beyond a chosen runtime profile;
- unknown keys.

WAE scans from `0000` and stops at the first missing section. That is implementation-specific behavior and is not suitable as the project's default discovery policy because a gap would silently discard later definitions.

Recommended typed policy:

1. classify all section-name candidates;
2. normalize valid four-digit indices;
3. reject or diagnose duplicates;
4. sort numerically in one central component;
5. preserve gaps;
6. decide gap legality separately from discovery.

## 6. Profile descriptor

Recommended data-driven model:

```text
TheaterProfileDescriptor
- TheaterKind
- ControlIniLogicalNamesLowToHigh
- TmpExtension
- OptionalFallbackTmpExtensions
- IsoPaletteLogicalName
- UnitPaletteLogicalName
- OptionalResourcePaletteNames
- ContentScope
- KnownGeneralKeySchema
- TileSetSectionGrammar
- VariationPolicy
- EvidenceLevel
```

The descriptor is serializable and versioned. It contains no Unity objects.

## 7. RA2 versus YR and extension engines

Theater control behavior can be extended by editors and MOD engines. Examples include:

- extra ground/LAT pairs;
- custom connected TileSet lists;
- custom palettes;
- expanded theater sets;
- additional fallback file extensions;
- alternate TileSet naming and variation rules.

These must use named profiles. They are not proof of vanilla RA2/YR behavior.

## 8. NewUrban fallback

WAE documents an FA2-specific fallback from `.ubn` to `.urb` because some Marble Madness resources for NEWURBAN are absent in the expected extension.

Project treatment:

- record it as `ImplementationSpecificBehavior` in an editor compatibility profile;
- disable it in the strict vanilla resource resolver unless ProjectBaseline evidence or original-runtime evidence confirms it;
- preserve both primary and fallback candidates and their provenance;
- never silently relabel an `.urb` asset as an `.ubn` asset.

## 9. Composition boundary

Theater control composition produces an effective logical document before typed registry construction. Typed parsing must not mutate the lossless document.

Map-local Rules/Art overrides do not automatically modify theater control INIs. A separate explicit profile is required if a MOD engine allows map-local theater-registry changes.

## 10. Diagnostics

Suggested diagnostics:

- missing `[General]`;
- invalid TileSet section suffix;
- duplicate normalized TileSet index;
- TileSet index gap;
- missing required key;
- invalid integer/boolean;
- special-set reference out of range;
- palette or extension missing from profile;
- unsupported extension key;
- fallback asset used;
- source composition provenance incomplete.
