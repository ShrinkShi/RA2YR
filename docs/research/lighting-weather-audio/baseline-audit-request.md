# ProjectBaseline Sanitized Audit Request

> **Source notice:** ChatGPT Web public-source research. ProjectBaseline was not read. Not a Codex artifact. No GPL or unclear-license code was copied, translated, mechanically rewritten, or ported. `code_imported: false`.

## Status

This is a design for a future read-only audit. It was not executed.

Any observation generated by the future audit has evidence grade:

```text
ObservedByFutureProjectBaselineAudit
```

It cannot be promoted automatically to `ConfirmedByOfficialRuntimeSource`, and it cannot by itself update the compatibility matrix.

## Purpose

The audit should answer aggregate questions about:

- `[Lighting]` section and field presence;
- raw numeric parse shapes;
- normal/Ion/Dominator profile completeness;
- broad static/time-style categories;
- weather capability metadata;
- Theme/Sound/media reference binding status;
- local-light type/reference prevalence;
- Fog/Shroud metadata;
- environment Trigger command categories;
- input-path equivalence;
- diagnostics and policy conflicts.

It must not reveal or reconstruct a specific map's environment design.

## Sample-selection design

Selection should be stratified without publishing map identity.

Suggested broad categories:

- all six stock Theater categories where available;
- campaign;
- skirmish;
- multiplayer;
- cooperative/client mode candidate;
- tutorial/challenge candidate;
- small, medium, and large geometry buckets;
- no `[Lighting]` candidate;
- ordinary daytime-style candidate;
- dark/night-style candidate;
- strongly tinted candidate;
- Ion/Weather capability candidate;
- alternate Ion-profile candidate;
- Dominator-profile candidate;
- Theme present/absent;
- local-light-heavy candidate;
- Fog/Shroud variation;
- extension/unknown environment fields;
- malformed or duplicate metadata candidate.

SelectionBasis can describe only the broad category and sampling method. It cannot expose names, paths, hashes, exact values, or identifiers.

## Read-only constraints

The future audit must not:

- modify maps;
- rewrite INI;
- repair numeric text;
- select or alter Lighting profiles;
- resolve resources by extracting or publishing bytes;
- start RA2/YR, Unity, FinalAlert, WAE, XCC, or a renderer;
- generate screenshots, previews, audio, or videos;
- create new maps;
- execute Trigger actions;
- create weather, visibility, lighting, or audio state;
- update compatibility, ADR, third-party ledger, or `.dev-records`.

## Input modes

For the same selected logical sample, the audit should compare:

```text
Memory input
seekable Stream
non-seekable Stream
short-read Stream
bounded MIX window
```

The public result may state equality or mismatch categories only. It must not expose source bytes or paths.

## Privacy and anti-reconstruction controls

- predeclare bucket boundaries;
- suppress groups below a configured minimum size;
- merge rare categories into `Other`;
- do not publish per-sample ordering;
- do not publish timestamps;
- do not publish exact counts when the sample group is extremely small; use bounded categories;
- salt or avoid any internal per-sample hash in public output;
- review cross-table joinability;
- keep raw audit artifacts local and outside the repository unless a separate approved process exists.

## Audit procedure design

1. Select samples by hidden identity and public broad category.
2. Read the map through bounded input adapters.
3. Parse using the existing lossless INI layer.
4. Produce raw environment candidates without defaults or repair.
5. Run explicit candidate policies in audit-only mode.
6. Produce consistency diagnostics.
7. Compare input modes.
8. Aggregate and suppress rare categories.
9. Validate the public schema against the forbidden list.
10. Publish only aggregate output after manual review.

## Failure handling

A failed parse can publish only:

- broad failure category;
- diagnostic code;
- input mode;
- whether all input modes agree;
- whether a configured budget was reached.

It cannot publish the offending raw value.

## Compatibility boundary

Audit results can:

- refine test priorities;
- identify common spelling/profile categories;
- identify missing public evidence;
- support future implementation design;
- produce `ObservedByFutureProjectBaselineAudit` observations.

Audit results cannot:

- mark a format fully compatible;
- prove original runtime behavior;
- select a lighting formula;
- legalize source-code reuse;
- replace executable acceptance tests;
- update compatibility without a separate reviewed decision.
